# Generated code in this repository, and how to regenerate it

_Verified against vpay `b747e5d5` (2026-09-23). Version-sensitive claims
carry the date they became true — see [VERSIONING.md](https://github.com/vaam-apps/vpay-skills/blob/main/VERSIONING.md)._

## There is no OpenAPI spec and no OpenAPI codegen

Say this out loud before reaching for a generator. Searching the `justfile` for
`openapi` returns nothing, and `schemas/` holds two files as of 2026-09-23 —
`vpay.cstack`, the CrateStack schema that compiles into `vpay-db`, which is a
_database_ schema, and `privacy-inventory.yaml`, the personal-data
classification `verify-privacy-inventory` checks against the migrations
(since 2026-09-18, vpay#187). Neither is an SDK input. _(This said "one file"
until 2026-09-23.)_

**Both merchant SDKs are hand-written** against the wire contract in
`docs/flows/merchant-auth.md` and the flow documents.
`cargo xtask verify-sdk-parity` is what keeps them in step — see
`references/parity.md`. There is nothing to re-run after changing a route; there
is a method to write in each SDK, a test to write in each, and a row to edit.

Two things _are_ generated.

## 1. Pigeon — the Flutter platform channel

**Spec:** `sdks/flutter/vpay_checkout_flutter/pigeons/checkout.dart`.
**Definitions only**, and the **frozen contract** between the Dart core and
every platform host. D7: _"Pigeon rather than a raw `MethodChannel` because the
channel carries a credential and an untyped `Map<String, dynamic>` across three
languages is where that gets mistyped."_

Outputs, all committed:

| File                                                                         | Language |
| ---------------------------------------------------------------------------- | -------- |
| `lib/src/platform/messages.g.dart`                                           | Dart     |
| `android/src/main/kotlin/dev/vpay/checkout_flutter/Messages.g.kt`            | Kotlin   |
| `ios/vpay_checkout_flutter/Sources/vpay_checkout_flutter/Messages.g.swift`   | Swift    |
| `macos/vpay_checkout_flutter/Sources/vpay_checkout_flutter/Messages.g.swift` | Swift    |

**Regenerate the Dart side** (from the package root):

```bash
dart run pigeon --input pigeons/checkout.dart
```

That reads the `@ConfigurePigeon(PigeonOptions(dartOut: …))` block in the spec,
which names **only** `dartOut`. Native outputs are produced by passing
`--kotlin_out=…` / `--swift_out=…` on the command line — pigeon's CLI flags
override `PigeonOptions` per invocation, deliberately, so adding a native target
never requires editing the spec. **There is no `just` recipe for any of this.**

### The trap: a hand-added import that regeneration will drop

`lib/src/platform/messages.g.dart` opens with the usual _"Autogenerated from
Pigeon (v29.0.1), do not edit directly"_ banner — and then carries, a few lines
down:

```dart
// Hand-added after generation (2026-09-14): see ShowCheckoutRequest.toString.
import '../redaction.dart';
```

It is there because D6 requires the **generated** channel types to redact too:
a hosted session's URL carries the session secret in its fragment, and a
`toString` that renders it is how the redaction regresses. Re-running pigeon
**silently removes that line**, and the file will not compile — but if you
resolve that by deleting the `toString` rather than restoring the import, the
redaction goes with it.

`test/messages_redaction_test.dart` is what notices. It has its own `✅` row in
`docs/sdks/parity.md` — _"The **generated** channel types redact too (D6:
'generated code is how this regresses')"_ — asserting the session URL is never
rendered, that the redaction **survives string interpolation** (which is how it
would actually be logged), and that a null `reachedUrl` renders as `null`
rather than as a zero-length string.

After regenerating: re-apply the import, run `just test-flutter`, and confirm
that suite is still green.

`pigeons/checkout.dart` also says, in its own header, that the lane which
implements against it **must not change it**. The shape of `ShowCheckoutRequest`
and `CheckoutWindowEvent` is the contract; if you need a new field, that is a
deliberate widening (as D8's `mode` field was), not a refactor.

## 2. ZenStack — the demo shop's database client

`examples/shop/zenstack/schema.zmodel` is the source. Regenerate with:

```bash
pnpm --filter @vpay-examples/shop generate
```

(= `DO_NOT_TRACK=1 zen generate`). It is also the package's `postinstall`, so a
plain `pnpm install` runs it.

Migrations live in `examples/shop/zenstack/migrations/` with a
`migration_lock.toml`. They are the **shop's** migrations, not vpay's — vpay's
are `backends/migrations/`, whose bytes are checksummed and which are
prettier-ignored for that reason (issue #76). Do not reformat either set.

Two pnpm overrides exist because of this generator, and their dated prose
explains why. ~~in the root `package.json`'s `"//pnpm"` array~~ — **moved
2026-09-19** (vpay#217, which also pinned pnpm 11): the `overrides:` block and
its reasons are in `pnpm-workspace.yaml` now, the reasons as `#` comments
above it. The two: `@prisma/config>deepmerge-ts`
(a `--prod` advisory, because `@prisma/client` is a production dependency of
`examples/shop`) and three scoped `*>lodash` entries under `chevrotain`, which
arrives through `zenstack > @zenstackhq/language > langium > chevrotain`. The
`chevrotain` entries were measured by regenerating `prisma/schema.prisma` byte
for byte with the override applied, because grammar analysis is what
`zen generate` actually runs.

## Build outputs, not committed

`sdks/nodejs/dist` and `sdks/stripe-js/dist`, both `tsc -p tsconfig.build.json`,
wired as each package's `prepack`. They are gitignored, and several things
depend on them existing:

- `@vpay/checkout`'s `deps` script and `examples/shop`'s `build:deps`
- `@vpay/e2e`'s `deps` script
- `sdks/stripe-compat`'s `deps` script
- since 2026-09-22, `@vaam-apps/vpay-tauri-checkout`'s `deps` script (it
  builds `@vaam-apps/vpay-stripe-js`), and `examples/tauri-checkout`'s,
  which builds the plugin in turn
- `just lint-web`, which depends on `build-sdk-node` — because
  `sdks/stripe-compat` imports `@vaam-apps/vpay-sdk/stripe`, whose types
  resolve through the package's `exports` map to `dist/stripe-auth.d.ts`.
  Without the build, a clean checkout fails with
  `TS2307: Cannot find module '@vaam-apps/vpay-sdk/stripe'` — a missing artefact
  reported as a broken import.

If a typecheck fails on a missing module in a package that imports an SDK, run
`just build-sdk-node` before believing the error.
